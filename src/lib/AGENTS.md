# src/lib rules
- Prospect identity uses catalog, the ML catalog search result with the exact same catalog ID (first check-digit-valid GTIN), or exact catalog-linked offer/variation EAN only; missing EAN does not count toward discovery targets, and fiscal suggestions use exact supplier barcodes with mandatory review, never title similarity — why: avoid importing another variant's identifier or guessed tax classification.
- Marketplace IDs remain shared; company_marketplace_fees stores company commissions and all price/store calculations and order imports resolve fees by company — why: changing one company's commission must not affect another or break existing store links.
- Bling custom fields (reads, bulk/single-product edits, auto roles) run as resumable bling_custom_field_jobs via custom-fields-tick using PATCH camposCustomizados only, explicit non-empty scopes and batched snapshots; local resets are service-only and blocked by active jobs/leases — why: PATCH keeps other fields, edits never widen scope, and cleanup never writes to Bling.
- The Bling queue panel aggregates ordinary sends and current custom-field send jobs in one products/requests display, sharing the company overview query and counting actual custom-field log rows plus outstanding work for requests; cancelled and older jobs stay out of progress — why: one compact panel must reflect sends without counting unchanged products as API calls; details stay in Logs.
- Automatic custom-field Anatel values use the pure custom-field-anatel helper — why: test fallback handling without changing Anatel descriptions or audit rules.
- Custom-field automatic mapping renders company definitions as rows and adapts field-first choices to existing role-to-field storage — why: real Bling names remain authoritative without changing persisted assignments.
- Fixed custom-field role values live in a browser-safe pure module used by the worker and unit tests — why: numeric and written warranty choices can be verified independently of Bling calls.
- Custom-field dropdown options come from GET /campos-customizados/{id} (opcoes) and are stored in bling_custom_fields.opcoes/tipo_campo_id; the pure custom-field-options module decides which values a list field accepts — why: a value outside the Bling list must be caught in the UI before any Bling write.
- Custom-field definition discovery requires a Products module returned by the destination connection, validated in custom-field-modules; absent modules surface an access warning instead of zero-field success — why: Bling can return HTTP 200 with an empty module list when fields are not accessible.
- Stock automations use the pure supplier-freshness helper: failed downloads fall back to the last complete base (last_ok_sync_at) within 12 h, recent failures are not retried per company, runs heartbeat while waiting and a per-schedule lease blocks duplicates — why: one slow supplier must not time out every company, yet older data must still stop runs to avoid zeroing stock.
- Quick-collect prospect searches skip only the photo minimum during discovery; photos are completed from the exact-EAN supplier catalog and three JPG/PNG photos are required in the pre-import review — why: more candidates reach review without relaxing what goes to Bling.
- Prospect import first prepares each selected item (exact-EAN local sources, then cited web research via the AI Gateway Responses SDK for missing brand/NCM/Anatel/measures/description); items preparation left 100% complete (no missing data, audit blocker, identity note or error; pure ml-prospect-ready) are imported in one click with the found values recorded as reviewed (no per-product confirmation), then re-audited before the send; the Bling send queue from earlier items of the batch does not block later ones, and the ML supplier contact (Código ML) is reused or created in the destination Bling at import — why: the user chose automatic filling, while only sourced values and fully complete products reach Bling.
- Product creation in Bling (criar and 404 fallback) includes the company's automatic custom-field values (custom-field-auto-values, list options validated; retried without them on a 400) and stores them locally; garimpo products get the daily ML stock rule at import and their stock send is queued by finish_bling_push_created — why: new products must reach Bling complete instead of with zero stock and empty fields.
- Supplier spreadsheet batches persist and validate one chosen SKU prefix; product creation still resolves the destination supplier automatically from that actual prefix — why: the same supplier can own multiple prefixes, while Bling contact IDs remain company-specific.
