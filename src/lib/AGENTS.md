# src/lib rules
- Prospect identity uses catalog, the ML catalog search result with the exact same catalog ID (first check-digit-valid GTIN), or exact catalog-linked offer/variation EAN only; missing EAN does not count toward discovery targets, and fiscal suggestions use exact supplier barcodes with mandatory review, never title similarity — why: avoid importing another variant's identifier or guessed tax classification.
- Marketplace IDs remain shared; company_marketplace_fees stores company commissions and all price/store calculations and order imports resolve fees by company — why: changing one company's commission must not affect another or break existing store links.
- Bling custom fields (reads, bulk/single-product edits, auto roles) run as resumable bling_custom_field_jobs via custom-fields-tick using PATCH camposCustomizados only, explicit non-empty scopes and batched snapshots; local resets are service-only and blocked by active jobs/leases — why: PATCH keeps other fields, edits never widen scope, and cleanup never writes to Bling.
- The Bling queue panel aggregates ordinary sends and current custom-field send jobs in one products/requests display, sharing the company overview query and counting actual custom-field log rows plus outstanding work for requests; cancelled and older jobs stay out of progress — why: one compact panel must reflect sends without counting unchanged products as API calls; details stay in Logs.
- Automatic custom-field Anatel values use the pure custom-field-anatel helper — why: test fallback handling without changing Anatel descriptions or audit rules.
- Custom-field automatic mapping renders company definitions as rows and adapts field-first choices to existing role-to-field storage — why: real Bling names remain authoritative without changing persisted assignments.
- Fixed custom-field role values live in a browser-safe pure module used by the worker and unit tests — why: numeric and written warranty choices can be verified independently of Bling calls.
- Custom-field dropdown options come from GET /campos-customizados/{id} (opcoes) and are stored in bling_custom_fields.opcoes/tipo_campo_id; the pure custom-field-options module decides which values a list field accepts — why: a value outside the Bling list must be caught in the UI before any Bling write.
- Custom-field definition discovery requires a Products module returned by the destination connection, validated in custom-field-modules; absent modules surface an access warning instead of zero-field success — why: Bling can return HTTP 200 with an empty module list when fields are not accessible.
- Stock automations use the pure supplier-freshness helper: failed downloads fall back to the last complete base (last_ok_sync_at) within 12 h, recent failures are not retried per company, runs heartbeat while waiting and a per-schedule lease blocks duplicates — why: one slow supplier must not time out every company, yet older data must still stop runs to avoid zeroing stock.
- Quick-collect prospect searches filter only by delivery deadline, price/cost and exact EAN (no photo, ingestible or weight/length filter during discovery); everything else is completed at import, and import still enforces the audit, three photos and the 30 kg/70 cm caps — why: more candidates reach preparation without relaxing what goes to Bling.
- Prospect preparation looks up Anatel in the own bases (anatel_products by EAN variants or by the SKU of supplier/Bling products with the same EAN, then official homologations by exact model code with matching brand and a single number); when none is found it sets "Não se aplica" — why: the user decided an EAN absent from the Anatel base is not applicable, without any AI.
- Prospect import first prepares each selected item (exact-EAN local sources, then the ML catalog by exact EAN (ml-ean-lookup) for empty measures/brand/description/photos, then Amazon Brasil SP-API catalog by exact EAN via amazon-catalog(.server) filling only empty NCM/brand/weight/full box/description and photos below three, skipping multi-unit packs, ; no credit-consuming AI or web research — the user forbade it, so anything these free sources lack stays pending); items preparation left 100% complete (no missing data, audit blocker, identity note or error; pure ml-prospect-ready) are imported in one click with the found values recorded as reviewed (no per-product confirmation), then re-audited before the send; the Bling send queue from earlier items of the batch does not block later ones, and the ML supplier contact (Código ML) is reused or created in the destination Bling at import — why: the user chose automatic filling, while only sourced values and fully complete products reach Bling.
- Product creation in Bling (criar and 404 fallback) includes the company's automatic custom-field values (custom-field-auto-values, list options validated; retried without them on a 400) and stores them locally; garimpo products get the daily ML stock rule at import and their stock send is queued by finish_bling_push_created — why: new products must reach Bling complete instead of with zero stock and empty fields.
- Supplier spreadsheet batches persist and validate one chosen SKU prefix; product creation still resolves the destination supplier automatically from that actual prefix — why: the same supplier can own multiple prefixes, while Bling contact IDs remain company-specific.
- Multistore link sheets come from the service-only multistore_export_page RPC (read-only; same cost formula as transform_update_price_stock with the store's company marketplace fee, falling back to current store/product price) and the pure multistore-export module for the Bling CSV layout — why: the sheet must price like the automations without writing prices, and layout rules stay unit-tested.
- "Novos do fornecedor" lists supplier products missing from the company via the service-only supplier_catalog_candidates/summary SQL (same cost/weight/length limits as the pure supplier-catalog-draft module) and imports them as supplier_catalog_import_jobs driven by a 10 s bank cron with fenced leases; data is completed from the supplier, exact-EAN suppliers/Bling and the ML catalog by exact EAN, every photo is checked, all active rules run on a virtual product, and only complete_supplier_catalog_item (modo 'importar' only) creates the product (price/stock recomputed by supplier_catalog_quote) and inserts its own 'criar' queue row; modo 'escanear' jobs run the same preparation/audit and store per-product results in supplier_catalog_scan, which 'Importar prontos' (only_ready) uses before re-checking everything — why: rejected products never enter bling_products, a scan can never write to Bling, and per-product creation must not clear other pending sends.
- enqueue_bling_push clears only the requested products' queue rows when product IDs are given — why: a scoped call must never drop other products' pending creations.
- Login security: db_pre_request enforce_account_security blocks authenticated PostgREST calls lacking an email-code session or a <365-day password; passwords change only via server functions writing a grant the auth.users trigger consumes — why: enforcement covers tables, RPCs and server functions without trusting the browser.
- Garimpo weight/size limits pass through prospectLimits, which caps any job value at 30 kg and 70 cm, and the import refuses incomplete measures — why: no prospect above those limits may reach Bling even from older jobs.
- A 403 on the ML catalog offers list (/products/{id}/items, PolicyAgent) pauses the prospect job via params.ml_offers_blocked_until (pure ml-prospect-block, 10-minute retries driven by the watchdog) and returns those candidates to pending instead of discarding them; the pause diagnoses the cause per ML's 403 guide (pure ml-403 parses body/PolicyAgent headers and ranks app blocked/disabled, inactive user, scopes, IP, token owner, PolicyAgent; ml-403.server checks /applications, /users/me pending codes and the same call without token, cached 10 min) and stores it in params.ml_offers_block and the job message; every other ML caller reports refusals through mlHttpError (ml-http.server), and failed daily stock refreshes and mapping batches record that reason (ml_product_matches.error, ml_map_jobs.error) while keeping values — why: an account-wide ML block is not a product defect and must not burn through the search. ML mapping (map-tick and single-product mapping) keeps existing ml_product_matches and leaves SKUs unchecked when the ML call errors; daily recotation keeps the last values — a blocked API must never delete links or zero stock.
- Every Mercado Livre API call goes through mlFetch (ml-http.server): one database-arbitrated slot per call shared by the whole app (take_ml_app_slot, spacing from the pure ml-rate-limit module at 80% of the official 18,000 req/h per Client ID), 429 pauses all callers (pause_ml_app) with Retry-After/backoff+jitter, and exhausted limits raise MlTransientError so jobs requeue instead of discarding products — why: the quota is per application across every company, task and Worker.
- The category browser uses authenticated, company-checked pagination over the bundled official taxonomy, sharing it with classification — why: the displayed categories must match the categories the system can suggest.
- Category batches use fenced database leases, atomic item/progress RPCs and a cooldown scheduler; optional AI traverses the bundled official ML taxonomy through streamed Lovable Responses calls — why: every selected product stays tracked without invented categories, duplicate work or automatic approval.
