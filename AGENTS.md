- Published server bundles guard createRequire(import.meta.url), including minified aliases, with Nitro's file:/// fallback — why: the fetch-bundle target can omit Cloudflare's guard and Worker module URLs are undefined at startup.
- Subdirectories have their own AGENTS.md (e.g. src/lib/AGENTS.md for custom-field rules); read it before changing files there.
- Bling API calls acquire a database-arbitrated company slot shared across every task and Worker — why: parallel requests cannot bypass the per-company rate limit, while different companies remain independent.
- NCM audit suggestions resolve exact supplier SKU matches through the central prefix map and require per-product review before writing — why: Mercado Livre catalog searches do not expose fiscal NCM and classification must not be guessed.
- Image correction previews supplier/EAN or accessible-company SKU matches; company donors must be active, linked and audit-clean; apply rechecks every photo in one-product requests with six concurrent checks — why: invalid photos must not survive review and bulk applies must fit Worker limits.
- Image audits recheck every photo per run (cache rows count only if checked after run start), read headers via a 1-byte Range GET and fully download only sizes/hosts matching known placeholders (audit_placeholder_signatures), retry 429/5xx; batches of 500, bulk cache lookup/upserts, encoded-size GET filters, and IMAGE_AUDIT_SHARDS workers (6 downloads each, optimistic cursors); advance only fully checked prefixes — why: respect Worker limits, never skip photos or reuse old results.
- Audit progress uses a shared layout badge polling company audit-runs without driving jobs or blocking navigation — why: progress stays accessible across pages while workers continue independently.
- Corrected-only audits are general company-scoped actions in Products and Audit, using the database's accumulated pending changes rather than the visible filter or last correction; they reuse the preceding run's rules and active-only context (inactivated corrections leave the audit) and consolidate untouched findings after the extra-rule engine, clearing only changes covered by successful completion — why: corrections from any source stay pending without losing other products' results or concurrent corrections.
- Audit runs finish through a bank-cron job the watchdog schedules for runs idle 2 minutes (schedule_audit_finish/resume_audit_run), never inside the photo tick; at most 4 finishes run at once (advisory slots in resume_audit_run), and the photo rule joins the cache in one set-based query, others wait for the next cron minute — why: the final SQL pass takes ~40s for 14k products while internal HTTP calls are cut at 60s, so abandoned runs stayed "em andamento" and blocked new audits.
- Product Mercado Livre categories live in product_ml_categories, separate from Bling product category fields; use official title-based category discovery when catalog product searches are unavailable and require per-product approval — why: categorization must still work without catalog access without triggering Bling writes or overwriting its existing category.
- Bling existence cleanup snapshots company product IDs, verifies structured 404 twice after API health checks, and deletes only unchanged local products in a fenced atomic RPC with retained evidence — why: connection errors, changed IDs and cancelled workers must never remove valid products.
- Bling existence workers select the oldest due next_tick_at before started_at — why: every company gets a turn instead of the earliest jobs monopolizing all batches.
- Company-scoped accounts use a separate company_viewer role, default-deny server-function allowlists and restrictive database policies/function guards — why: hiding navigation alone cannot prevent direct writes, secret reads or cross-company access.
- Company accounts share canonical company rows with administrators; shared ML offers require an RLS-visible product and use database-derived SKU/EAN, while catalog status verifies membership and projects safe fields — why: parity must not duplicate data or expose another company's products or integration secrets.
- Company-scoped settings expose only the account's own password change through Auth with current_password; profile editing remains unavailable — why: password self-service must not widen company permissions.
- Auth user emails are the canonical login identity; admin listings prefer them and an auth email-update trigger synchronizes profile display emails — why: renamed company logins must never keep showing legacy provisioning addresses.
- Auth INSERT consumes an expiring email-bound nonce issued by service-only authorize_account_creation after adminCreateUser checks roles — why: block signup/replay without depending on app_metadata timing.
- Stock source selection uses consider_ml_stock in manual RPCs and persisted schedule options, defaulting to true for legacy callers; SQL guards ML floors and attribution with the same flag — why: disabling ML must affect calculation, not just the controls.
- Repasses use a separate company-scoped ledger with authenticated member-only CRUD and database-generated results; totals cover the whole filtered period independently of pagination — why: settlement entries must not duplicate order revenue or DRE expenses, and all accounts must share canonical company records.
- Repasse saves expand the visible date period to include the saved date and reset pagination — why: a successful save outside the current period must not appear to lose the entry.
- Evolusom supplier data is read from its paginated API in resumable chunks (fornecedores.sync_cursor) by /api/public/suppliers/evolusom-tick every minute; automations treat 'parcial' as fresh — why: a full read takes ~13 min under the 10 req/min limit.
- Supplier spreadsheet imports persist one explicitly selected SKU prefix per batch; destination Bling supplier resolution remains automatic from the real prefix/contact map — why: multi-prefix suppliers need deterministic SKUs without reintroducing source-company contact IDs.
- R2 image propagation marks changed products dirty; supplier-sheet image-only updates enqueue a full product PATCH after propagation, while new products wait for propagation before their create item is queued — why: a successful local image replacement must not remain only in the database or let a new product reach Bling before its final signed URLs exist.
- Description corrections use visible plain text for minimum length, normalize warranty/Anatel/Anvisa in one deterministic write and always mark the product dirty; new supplier products use newlines instead of HTML breaks — why: tags must not satisfy content rules, asynchronous cleanup must not race the footer, and local edits must remain eligible for Bling propagation.
- Email grants (Nango primary, Nylas rollback) store only provider identifiers; Nango Connect sessions are user-bound and request read-only mailbox scopes, verification codes are sender-allowlisted, AES-GCM encrypted, short-lived and audit-logged, and provider secrets never reach the browser or database — why: mailbox passwords, OAuth tokens and plaintext authentication codes must never reach storage or an untrusted request path.
- Nango connections persist only a credential slot (never the API key): new connections fill slot 1 to NANGO_CONNECTIONS_PER_KEY and then slot 2, while every later proxy, ownership check and revocation reuses the recorded slot — why: connections belong to the Nango workspace that created them and cannot safely fail over to another key after creation.
- Local Bling write tests require BLING_RUNTIME_ENV=local_test plus an isolated Supabase project confirmed by the launcher and server guard — why: local experiments must never inherit production credentials, tokens or queues.
- Cross-company creation resolves destination contacts by longest central SKU prefix and Bling contact Código (bling_supplier_prefix_contacts, refreshed in supplier sync), falling back to bling_supplier_map; confirms the link and retries reuse the created ID — why: IDs are company-specific and names repeat.
- Supplier writes update an existing product-supplier link even when its contact is undefined, preserving purchase price and confirming the intended contact; retries keep queue uniqueness and skip conflicting active work — why: Bling retains unassigned link IDs and recreating them causes duplicate records.
- Supplier dimension correction uses central prefixes or unambiguous exact prefixless SKUs in active company/global catalogs, preserves positive values and reports unmatched codes separately from absent attributes — why: never invent measurements.
- The app-tick cron (every minute) runs worker-watchdog to re-enqueue stalled chained jobs (custom fields, suppliers, Bling/store sync, ML map/prospect, CDN images) — why: queues must keep moving with no user logged in; ticks are lease-guarded so extra kicks are harmless.
- Supplier catalog foto stores every supplier image joined by "|" (Oderço, Evolusom, Hayamax) — why: image corrections need all supplier photos, not only the first.
- Per-deposit stock keeps one 'estoque' queue item per product; prepare_deposit_stock_targets flags each configured deposit (bling_product_deposit_stock), and the worker posts one balance per flagged deposit, logging each call in requisicoes/depositos_log for progress and Logs; companies without fetched deposits keep the single default-deposit push — why: avoids changing queue uniqueness while sending only deposits whose value changed.
- CDN v2 URLs sign one canonical Base64URL-encoded R2 object with a per-integration key version; rotations are resumable jobs that GET/PATCH/GET complete Bling media, commit the database only after verification, keep the old key in grace, and require exact residual-link, external-consumer, purge and canary gates before revocation — why: a leaked URL must not open the bucket and key changes must never break unconfirmed product or marketplace links.
- The isolated unit suite runs through `npm run test:unit`, blocks real network/privileged credentials, adapts legacy `node:test` imports in memory, and writes a concise ignored report under `tests/unit/reports` — why: regression checks must run unattended without touching Bling, Supabase, Cloudflare or other production services.
